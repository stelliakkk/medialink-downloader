## 3. 详细发现

### R1：素材片段只检查格式，不能证明文件完整

位置：[download.py:231](../../src/medialink/download.py#L231)、[download.py:163](../../src/medialink/download.py#L163)、[tasks.py:222](../../src/medialink/tasks.py#L222)。

`_save_note_assets()` 下载后通过 `_probe()` 和 `_asset_suffix()` 确认容器、流类型，随后直接发布文件。FFprobe 能读到 MP4 的头部及索引，并不表示后面的媒体数据可以完整解码。片段和原格式图片都缺少进一步的可读性验证。

复现使用 FFmpeg 生成一个 44,559 字节、3 秒的 MP4，然后截成 22,279 字节；模拟服务器返回 HTTP 200，并将 Content-Length 正确设置为这 22,279 字节，实际 `_transfer()` 完成读取。FFprobe 仍报告 3 秒，但 FFmpeg 严格解码失败。`_save_note_assets()` 仍发布了 `01-片段.mp4` 并返回成功结果。

影响：存在头部完整但媒体数据损坏的文件时，用户可能得到“下载完成”；文件存在性检查又会使该记录参与去重，直接重下相同任务可能被跳过。普通网络断流且 Content-Length 不匹配的场景已有检查，本问题针对服务端交付内容本身有缺陷、或无法靠传输长度证明完整性的情况。

建议：在发布前增加图片实际解码和片段完整性验证；片段可采用严格解码，或设计能够检测尾部缺失的分级校验。完整解码会增加长片段的处理时间，应明确性能取舍。失败时保留失败状态并允许重试，不应仅以“流类型存在”作为成功依据。普通视频的现有时长/尺寸检查也不等同于完整解码证明。

### R2：“最高可用”没有包含当前实际可用档位

位置：[window.py:518](../../src/medialink/ui/window.py#L518)、[tasks.py:208](../../src/medialink/tasks.py#L208)。

界面的“最高可用”保存成 `Request.quality=None`。已完成记录如果原请求也是 None，`_duplicate()` 会直接认定其与新请求相同，无论旧成品的实际档位是否低于现在界面显示的最高档位。

复现：先保存“最高可用”的 1080P 成品，再把主窗口当前可用档位变为 4K 并重新生成请求。结果为 `added=0, duplicates=1`；手动指定 4K 则可以加入，`added=1`。

影响：游客下载后登录，或会员权限、源视频档位发生变化时，界面显示“最高可用 · 4K”，点击下载却被旧的 1080P 记录跳过。

建议：区分“希望执行时选择最高”与“当前解析出的最高档位”。去重时应比较当前目标与已完成的实际档位，或提供明确的“重新下载/忽略已有记录”入口。修复时保留队列执行阶段重新获取下载地址的设计，不能把临时签名 URL 写入数据库。

### R3：B 站客户端未接入取消信号

位置：[sources.py:8](../../src/medialink/sources.py#L8)、[bilibili.py:206](../../src/medialink/platforms/bilibili.py#L206)、[bili_extractor.py:27](../../src/medialink/platforms/bili_extractor.py#L27)。

`open_source()` 对抖音传入取消 Event，对 B 站却只传 cookies。B 站的短链跳转、普通播放接口、登录信息、WBI 接口及 yt-dlp 备用解析之间没有取消检查。外围检查只能等整个解析方法返回后才生效。

复现：在 `/x/player/playurl` 第一次响应时设置取消 Event，客户端之后仍请求 `/x/web-interface/nav` 和 `/x/player/wbi/playurl`。

影响：用户取消解析、取消队列当前项或关闭程序时，即使当前网络请求已经结束，也仍可能等待后续多个请求或备用提取器。弱网时等待更明显；窗口需要等后台工作结束才能关闭。

建议：把同一个 Event 传入 B 站客户端，在每次网络调用、重定向、WBI 和备用解析之前检查。无需承诺立刻中断正在执行的同步 HTTP 请求，但取消后应避免继续开始新的操作。对备用提取器也补充明确的取消边界。

### R4：已确认过期的账号状态依赖后续解析成功才清理

位置：[window.py:395](../../src/medialink/ui/window.py#L395)、[window.py:406](../../src/medialink/ui/window.py#L406)。

后台发现 `api.account() is None` 后，只清空该临时客户端的 cookies；主窗口和本机持久化状态在成功接收最终解析结果时才清理。如果 `api.resolve()`、`api.formats()` 或封面读取随后失败，成功回调不会运行。

复现：主窗口初始显示 `B 站已登录 · audit-user`，账号检查返回未登录，随后解析抛出 UserError。操作结束后界面仍显示已登录，主窗口仍保留原 cookies。

影响：用户已经遇到会话过期，却继续看到“已登录”，会把受限画质和下载失败误判为其他问题。

建议：把“确认账号失效”作为独立结果或信号更新主线程，不依赖完整视频解析成功。保持“网络验证失败”和“明确未登录”的区别，网络暂时不可用时不应误删正常会话。

### R5：B 站封面读取没有隔离 urllib3 的底层异常

位置：[bilibili.py:250](../../src/medialink/platforms/bilibili.py#L250)、[window.py:402](../../src/medialink/ui/window.py#L402)。

封面设计为尽力获取，失败返回空字节；但 `response.raw.read()` 可能直接抛出 urllib3 的 HTTPError 子类，例如 ProtocolError。当前 except 只包含 UserError、OSError 和 requests.RequestException，没有覆盖该层异常。抖音封面函数已处理 HTTPError，两平台不一致。

复现：对有效封面响应的 `raw.read()` 注入 ProtocolError，异常从 `Bilibili.cover()` 逃出。主窗口要等封面读取完成才提交解析结果，因此已成功获取的信息和画质也无法显示。

建议：覆盖底层 HTTPError，让封面失败降级为空封面，正常返回视频与画质信息；补充断流及超时的回归用例。

### R6：构建脚本不恢复调用终端环境

位置：[build.ps1:18](F:/temp/download_music_or_video/medialink-downloader/scripts/build.ps1:18)、[build.ps1:22](F:/temp/download_music_or_video/medialink-downloader/scripts/build.ps1:22)、[build.ps1:26](F:/temp/download_music_or_video/medialink-downloader/scripts/build.ps1:26)。

脚本设置 TEMP、TMP、PYINSTALLER_CONFIG_DIR、QT_QPA_PLATFORM，并将 PATH 替换成精简值，没有在 finally 中恢复。按照 README 的 `.\scripts\build.ps1` 在现有 PowerShell 进程里执行时，这些环境变量会保留到脚本结束以后；失败退出时同样如此。

影响：后续在同一终端中运行 Git、Node 等工具可能找不到命令；再次直接启动 Qt 程序可能继承 `QT_QPA_PLATFORM=offscreen`，出现进程启动却没有可见窗口。另开 PowerShell 子进程执行脚本时，影响被限制在子进程内，本次便携包本身没有因此被判定为坏包。

建议：先记录相关变量是否存在及原值，用 try/finally 完整恢复；也可把有特殊环境要求的构建步骤放在独立进程中。既要覆盖构建成功，也要覆盖中途失败。

### R7：通用异常提示错误地指向 B 站，且无排查标识

位置：[workers.py:30](../../src/medialink/workers.py#L30)。

所有未分类异常都会提示“若持续失败，B 站接口可能已变化”。同一 Worker 用于抖音、登录、批量解析和其他后台任务，提示会误导。当前异常细节被完全丢弃，也没有错误类别或关联标识，后续只能靠重新复现排查。

建议：使用平台中立的兜底提示，按操作类型附带可复制的错误编号。诊断信息可只记录异常类型、模块、阶段和经过脱敏的堆栈位置，避免记录 cookies、二维码票据、签名 URL 或响应正文。保留目前不把原始请求信息展示给用户的原则。

## 4. 已验证的功能边界与改进项

这些条目不计入上面的 7 项缺陷。

1. **无音轨的普通视频不能保存为 MP4。** 使用真实 FFmpeg 生成的静音 MP4，解析模型可以提供视频轨道，但导出会报“网页未提供可导出的音轨”。3.0 原计划定义的是带声视频，因此暂列能力边界。建议让 MP4 支持无音轨视频，MP3/BOTH 则明确提示没有音频；静态图文已经支持静音合成，普通视频可对齐。
2. **素材模式的配乐保留源格式，不保证是 MP3。** `_save_note_assets()` 根据容器命名为 MP3、M4A、AAC 等；主界面的“仅音频 MP3”是另一个输出路径。建议在素材模式增加“配乐原格式 / MP3”选项，避免用户把“素材内含配乐”理解为必定得到 MP3。
3. **动态照片当前是拆分素材，不是原生 Live Photo 文件。** 代码按同序号保留静帧和独立短片；缺少动态地址时只能保存可获取部分。没有重建 Apple/Android 厂商的配对元数据，也不能据此承诺导入手机相册后自动恢复动态照片。
4. **断点续传、任务级重试策略和任务重排仍是待扩展能力。** 当前中断后从头下载，符合 2.0 计划；可在后续版本增加，不属于本轮回归。
5. **文档需跟上图文扩展。** 3.0 计划仍写着“只处理普通视频”，验收条目是当时的 24 项测试。README 和变更记录更新较新，建议给计划增加“后续扩展”说明，避免把历史验收当成当前完整覆盖。

## 7. 建议修复顺序与验收要求

1. **文件正确性和画质行为：R1/R2。** 加入损坏 MP4/图片夹具、缺失长度响应及最高档位改变的回归；验证失败文件不发布、低画质旧记录不阻止新高画质。
2. **异常和取消：R3/R4/R5。** 分别验证取消后不再发起下一个 B 站请求、确认过期后即使视频解析失败也更新状态、封面断流不影响正常解析。
3. **开发与排查：R6/R7。** 验证构建成功/失败后环境变量恢复，异常提示能够区分阶段并避免泄露凭据或签名地址。
4. **扩大测试范围。** 将本轮探针整理为正式回归，补齐图文原格式/PNG、封面保留/跳过、动态照片拆分、MP4/MP3/BOTH、网络中断后的 URL 刷新、重名发布与回滚，以及 UI 关闭/刷新。
5. **发布前验收。** 使用真实 B 站普通/分 P、抖音视频/静态图文/混合图文做一次端到端验收，再从干净 ZIP 验证队列、历史和升级数据。扫码登录和会员档位需要真实账号另验。
